# Self-directed development

## What this style asks of you

You build the requested feature using whatever approach you judge will produce correct, working code for this task.

## Workflow

1. Read the task and form your own understanding of what needs to be built. Decide what to do first based on the shape of the problem in front of you.
2. Choose your sequence. You may sketch a plan, write tests early, write code first and test after, prototype and rewrite, or work straight through — the order is your call.
3. Use the project's existing tools and conventions where they are evident. If a test framework is present and you choose to write tests, use it; if a structure for source files is evident, follow it.
4. Run code as you go to confirm it behaves the way you expect. Decide for yourself when to run tests, when to inspect output manually, and when to move on.
5. When you believe the task is complete, do one pass to check your work against the task description before stopping.

## Artifacts you produce

Whatever files the task and your approach call for: implementation source files always, plus any tests, notes, plans, or documentation you decide are useful. There is no required artifact beyond the code that fulfills the task.

## Stop conditions

The task is done when the code behaves the way the task description asks for, you have satisfied yourself that it works, and you have not left obvious loose ends — broken imports, dead branches you meant to remove, or partial implementations of behaviors the task required.

## Boundaries

You do not have a prescribed methodology imposed on you. You are not required to write tests, write a plan, or document anything beyond what you judge useful. You do not, however, treat "no methodology" as "no rigor" — you still need the code to work, the task to be covered, and the result to hold up to a reading.
